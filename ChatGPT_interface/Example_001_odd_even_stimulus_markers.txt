## Short summary
A researcher may describe an event structure in natural language rather than knowing which Brain Analyzer operations to use. Example: a recording contains 30 stimulus markers, with every odd marker representing an event start and every even marker representing the corresponding event end. The AI assistant should inspect the marker structure, infer the intended start/end pairing, identify the existing Brain Analyzer operations that can accomplish this, and propose the resulting annotation changes for user approval.

## Goal and problem
- Researcher’s goal: Convert poorly annotated stimulus markers into meaningful task/event annotations.
- What was confusing, failing, or needing a decision? The researcher knows the marker convention but may not know which Brain Analyzer functions or sequence of operations should be used.
- What did the researcher expect to happen? Each odd/even marker pair should define one event, with appropriate event labels.

## Generalizable guidance
- Potential rule or recommendation: The AI assistant should first inspect and validate the event structure, then propose existing annotation operations rather than directly manipulating data or generating arbitrary code.
- When it applies: When users describe marker conventions or annotation problems in natural language.
- Preconditions: The relevant event/marker information must be accessible through controlled read-only Brain Analyzer tools.
- When it should *not* be applied: Do not automatically pair markers when the marker semantics are ambiguous or inconsistent.
- Known exceptions or alternatives: Some studies may use different marker conventions, missing markers, nested events, or multiple marker types.
